# Request, job and browser-state recovery

These contracts define authentication, concurrent state updates, cancellation,
and recovery across the frontend, workers, and Redis.

- Enabled accounts come from a cached process snapshot of authentication configuration. Restart every frontend and WebSocket process after changing the configured account list. A removed account cannot use a persisted API session to extend its TTL; the next session read deletes it and clears the cookie. WebSocket handshakes and periodic session revalidation apply the same eligibility check. Session checks do no bcrypt work and do not initialize historical Redis user records. Existing session TTL/rotation rules still apply.
- Goal create, edit, delete and append-import operations retry against the latest Redis snapshot. Concurrent acknowledged changes are retained. The same protection covers autonomy configuration initialization/patches and run-list cancellation. An explicit replace import still intentionally replaces the list; an invalid empty import leaves it intact. Existing RedisJSON and plain-string arrays remain supported, including the Python worker's transactional updates. A sustained conflict returns an error instead of silently overwriting a newer snapshot.
- Image history and push subscriptions also update atomically. Image jobs and direct history submissions share the same history writer; deleting history removes owned assets only when the committed history no longer references them. Autonomous queue admission checks the 100-item limit atomically for both individual and batch submissions.
- Expiring root writes preserve plain-string records and atomically replace their value and TTL without a delete/recreate interval. Cancellation signals remain visible while another request renews them.
- Conversation list reads support mixed RedisJSON and plain-string records. Redis failures remain errors rather than appearing as an empty list. Finalization never writes the selected-conversation pointer.
- Conversation saves use optimistic concurrency with a server-issued token. Reads and successful saves return the record's `revision`; a save sends the revision its copy came from and is rejected with 409 and the current record when the stored revision differs. Browser clocks are never compared. On a conflict the browser re-applies only what that save changed (a rename, its own unsaved turn, its own outcome or Stop flag) to the newer record, so another device's turn or a worker-finalized answer is never overwritten. Records written without a revision (worker finalization, chat reservation, earlier saves) are identified by their server timestamp, and a first save may replace the empty reservation its chat request created. Clients that predate revisions keep the earlier timestamp comparison.
- The selected conversation is an id pointer. The tab's session cache remembers every selection, and the server pointer is saved when the user picks or creates a conversation; saving a conversation (including a background turn finishing) never changes either, and an automatic reselection after a deletion stays local. A reload opens the server's or the tab's selection only if history still contains it and otherwise opens a new conversation. Sending while the selected conversation no longer exists starts a new conversation instead of discarding the message.
- A save notifies the user's other sessions with only the conversation id and committed revision; a session that does not hold that revision reads the record, and a streaming conversation is left to the session running it. Deleting a conversation removes it from other open sessions.
- Deleting an owned conversation atomically signals its active job to stop, including a job still being initialized. No open browser is required. The worker retains finalization and capacity-release ownership; a late result cannot recreate the deleted conversation.
- Stream recovery retains its scan cursor across empty pages and keeps an executing entry pending when reclaim returns that same entry. Worker shutdown leaves deliveries received after draining begins for a replacement worker to recover.
- Assistant output is preserved even when it repeats an earlier answer. Text similarity does not prove transport replay. Existing job identity and stream-offset handling still deduplicate transport events. Compatibility utility exports preserve new and persisted answers without shortening them.
- Image jobs carry an execution owner and a 60-second lease, renewed every 15 seconds. Status queries, active-job recovery and new submissions classify expired work as interrupted and release its active capacity. Old records without leases receive 390 seconds from their last update to finish. Recovery never retries the provider request automatically: after interruption the provider may have completed it, so inspect existing outputs before submitting again. Partial output IDs remain available. The status record lasts one hour; this is explicit interrupted-state recovery, not a durable execution queue that resumes a provider request.
- Image job updates are fenced by the live owner and lease. A lost owner stops its local backend request and cannot publish a late successful result over the interrupted state. The active-job index uses atomic admission updates so concurrent submissions retain their records and respect capacity.
- Chat Stop preserves tracking and displays an error when cancellation is unsuccessful or unconfirmed. The UI announces a stopped response only after acknowledgment or reconciliation with a terminal job. Cancellation cannot undo operations already executed by an external tool.
- Fetch deadlines cover headers and body consumption. Callers must consume or cancel returned response bodies; callers that only inspect health status cancel the body explicitly. Caller cancellation continues to reach the body after headers. Profile import allows 150 seconds for the backend's bounded, staged profile replacement.
- Failed backend chat HTTP responses finalize from their status code and cancel their bodies immediately. A stalled diagnostic body cannot retain a worker slot, and raw backend diagnostics are not copied into saved chat errors. Backend admission rejections (409 for an active conversation, 429 for too many runs) are saved as an explanation of what to do rather than a bare status. A stream's terminal error keeps only the backend's own run outcomes (the fixed messages of its error event, such as a run timeout); other error text, unreachable backends, transport failures and Redis errors are logged and saved as fixed messages. Document ingestion saves a status-based explanation for a rejected request, without reading its body, and only the backend's own failure text for a failed ingestion.
- Finalization saves the conversation and then, in one Redis commit, records that save, releases the conversation and chat slot, clears streaming state, publishes completion and queues the turn for memory retention. A crash before that commit repeats only the saved-copy write; a guard is never released before the save is recorded, and a retry after a lost reply publishes nothing twice. The stream worker's retention poll sends queued turns afterwards, so neither completion, the worker slot nor the next turn in the conversation waits for the memory service. It retries a transient failure a few times with backoff (about two minutes) and does not retry a turn the backend rejects, for example when memory is not enabled. The backend derives the stored memory from the job and its content, so a repeated send is idempotent.
- WebSocket heartbeat deadlines are measured from the first unanswered ping. Delayed events from replaced sockets and cancelled reconnect attempts cannot invalidate the current connection. Chat subscriptions survive disconnection, polling requests do not overlap, and newer live progress takes precedence over an older in-flight polling response.
- Status polls, Stop, job subscriptions and steering authorize from the job request's owner and routing fields without reading the conversation history it carries. Chat subscriptions check the user's conversation set and the record's bound owner in one Redis call; saves write the record's `id` and `ownerId` first so the owner is read from its first bytes, and older records are read whole.
- The server accepts application messages only after it has authenticated the socket and sent `connected`. The browser treats a socket as connected, resets its backoff and (re)subscribes only on that message. After repeated failures it keeps retrying at the slowest backoff interval, and it retries at once when the browser comes back online or the window regains focus. When the socket returns, a tracked job's safety-net poll returns to its normal pace. The server also holds a bounded backlog of messages received before `connected` (closing with 1008 on overflow) and replays it in order, so older clients keep their subscriptions. An unsubscribe that arrives while ownership validation is in flight wins. A session-store outage at the handshake closes with 1013, which the browser retries; 4001 means the session is invalid.
- Live token events carry contiguous text with the offset of its first character. The worker sends the first delta after a quiet interval at once and combines deltas that arrive within the next 25 ms into one event; it never reorders tokens with the steps or other events on the same channel. A gap in live token offsets (after a reconnect, reload or late subscription) triggers an immediate status read, retried with backoff while the gap stays open; held tokens drain once the snapshot covers them. Tool steps follow the same rule: a status record without a step list (such as an OAuth prompt) keeps the steps already received, and snapshots merge with live steps without dropping or repeating one. The first status read after submit or resume is guarded like later reads, so live events received meanwhile are not rewound. A status that expired or was removed reconciles from the saved conversation, or reports that the status is no longer available, instead of leaving the conversation streaming.
- The browser keeps its local copy of the selected conversation only when it is at least as new as the server's. Progress for an assistant message that is missing from the local copy adopts the server's record instead of updating another answer. The browser saves a submitted turn once the server has accepted the chat request. It uploads a finished turn only when the worker did not save that outcome itself (an expired status, a rejected submission, Stop), and only from a copy that contains it.
- Submitted chat history is used as model input, but finalization persists the saved copies of earlier turns and appends only the new messages, so model-oriented copies (inline data omitted, attachment instructions appended) never replace saved content.
- The stream worker aborts a run only on explicit lease loss or once its lease validity window has elapsed; a transient renewal error inside the window is retried. The heartbeat also renews the conversation's cross-device streaming state while it still names the running job, so other devices keep the streaming indicator for runs longer than ten minutes. Renewal declares no placeholder keys, so it works for the ACL-restricted stream-worker Redis user.
- Chat submission writes a provisional status and user slot that expire after two minutes unless the job's request and status are written. The next turn in a conversation recovers a previous submission that stopped before queueing (no request or queue payload, no worker lease, conversation guard past its one-minute initialization grace): it replaces the guard and releases that job's slot, live status and streaming state. A submission whose provisional slot is gone when it writes its records fails with 503 instead of queueing. Stop finishes a live job that has no queue payload or worker lease itself rather than waiting for a worker.
- The backend start marker and the stop signal are checked in one Redis script. A Stop or conversation deletion recorded before that point, including during a reclaim's backend probe, prevents the backend request and is saved as a cancellation. Reclaim never replays a request that may have started: besides the evictable marker, streamed response or steps and a chat job's status past `pending` count as started. A started run whose owner lost its lease after a Stop is saved as cancelled, not interrupted.
- Browser responses and saved chat errors carry only messages written for users. Backend probe failures, which name pod addresses, and unexpected worker errors such as Redis failures are logged server-side and reported with fixed explanations.
- Conversation IDs follow one rule for chat submission, backend workspace scoping and WebSocket chat subscriptions: 1–128 ASCII letters, digits, `.`, `_`, `:` or `-`, starting with a letter or digit. Submission rejects other IDs with 400; generated UUIDs always match.
- Chat submission authorizes document attachments with the derived storage scope the upload routes use, never the raw session credential. Collection metadata is fetched only for a document-ingestion turn, which needs the backend's authoritative collection name and fails with 503 without it; attachments in replayed history never make a turn depend on Milvus.
- Login attempts are reserved atomically against every lockout counter before password verification, so concurrent guesses cannot bypass the limit. A failed verification keeps the reservation; success clears the username/IP counter and returns the shared reservations; infrastructure errors return all of them. Every verification performs one bcrypt comparison: an unknown username is compared with a per-process decoy hash at the highest configured cost, so response time does not reveal which accounts exist.
- A Google OAuth callback completes only in a browser signed in as the Daedalus user that started the authorization; the backend stores the grant under that user. Google's cross-site redirect cannot carry the SameSite=strict session cookie, so `/auth/redirect` returns a page that resubmits the callback to the same origin. The backend receives it only when that request's session owns the flow (the owner recorded with its callback target, or the chat job's owner for targets written by older stream workers). Other requests get 401 or 403, and the flow remains available to its owner.
- Document ingestion requires an explicit parsed completion event. Premature EOF, malformed completion and error events fail rather than producing a success message. LF, CRLF and CR framing are supported. Chat also requires an explicit completion signal and preserves partial output when transport EOF interrupts a response.
- An assistant error before its first token remains visible, including its retry action when recoverable. Concurrent image consumers share a fetch and retain distinct references; an image load finishing after its consumer unmounts releases the acquired URL.

Redis conversation history remains authoritative. The browser keeps only the selected conversation's id in sessionStorage; cache failures do not block server persistence. The service worker uses its own independent IndexedDB storage.

Redis arrays support both RedisJSON and plain-string storage. For rollback to a frontend without image-job leases, drain or wait for image jobs to finish first: that version cannot reconcile interrupted jobs. Legacy image requests receive the bounded grace period described above.

Regression coverage includes real loopback HTTP body/ingestion failures, concurrent RedisJSON and string goal mutations, actual image-owner process kill and lease expiry across a fresh process, component failure and cancellation states, WebSocket recovery, polling races, and complete server history despite browser cache failures. Model/provider success and physical-device behavior require separate environment-specific validation; these checks do not establish them.
